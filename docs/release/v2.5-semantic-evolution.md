# Evolve Studio V2.5 · Semantic Evolve Runtime

## 本版解决的问题

V2.4 已经能识别 PPT、代码、Excel 等物理成果类型，但仍然存在“成果类型过早决定流程”的风险。最典型的例子是 ZIP：ZIP 可能是代码仓库，也可能是融资资料、企业制度、培训材料、品牌素材、战略经营资料或任意业务包。

V2.5 将核心抽象改为：

> **Universal Evolution Protocol + Semantic Workflow Compiler + Native Artifact Runtime**

不再是 “Artifact Type → Fixed Flow”。

## 新执行链

```text
任意输入
↓
Container Inspector
物理上是什么？
↓
Artifact Graph Builder
里面真正有什么？组成关系是什么？
↓
Semantic Object Classifier
这些内容合起来是什么业务对象？
↓
Evolution Intent Compiler
用户究竟想让什么变好？
↓
Dynamic Workflow Compiler
这次项目真正应该怎么进化？
↓
Dynamic Acceptance Compiler
什么才算真的进化成功？
↓
Native Artifact Builders
每个成果按自己的结构修改
↓
Cross-artifact Validation
↓
Exact Accepted Snapshot
↓
Same-format Delivery
```

## ZIP 不再等于代码

ZIP extractor 返回：

```json
{
  "kind": "package",
  "manifest": [],
  "entries": [],
  "inventory": {}
}
```

Codebase 识别需要真实工程结构信号，例如：
- package.json / pyproject.toml / go.mod / Cargo.toml
- src/ / app/ / tests/
- 足够数量的代码文件

单纯在业务文档里出现 `API` / `schema` / `agent` 字样，不会把 ZIP 误判成软件项目。

## 业务对象识别

Deterministic draft 内置常见业务对象模式作为冷启动，但不是封闭枚举；Live AI Intake 可以输出任意新的 `typeId/label/domain` 和六步语义流程。

当前冷启动覆盖：
- 融资资料体系
- 企业战略经营体系
- 企业制度与人力体系
- 培训课程/教学体系
- 品牌资产体系
- 投资研究体系
- 营销活动体系
- 产品需求与设计体系
- 软件/AI系统
- 通用复合业务成果

## UI 原则

用户不需要学习几十种流程。顶部仍然只看到 6 个位置，但名称、输入、动作、产出和完成标准根据项目实时变化。

文件类型只在“物理成果与原生适配器”区展示，明确告诉用户：
- 这决定 Parser/Builder/Materializer；
- **不直接决定业务流程**。

项目内新增“业务对象理解”区，展示：
- 识别业务对象
- 置信度
- 业务目标
- 动态六步流程
- 跨成果联合要求

若识别错误，用户直接输入“这套成果实际是什么、用于什么场景”，系统使旧 Eval/Candidate/Release 失效并重新编译。

## Acceptance 真正随机应变

V2.5 把语义 Criteria 合并到正式 Acceptance Rubric：
- 用户真实目标
- 业务核心结果
- 原格式与交付完整性
- 多成果跨文件一致性
- 成果完整性
- 各原生 Artifact Adapter 专属 Criteria
- Protected Constraints

它们继续参与：

```text
Rubric → Eval Mapping → Baseline → Candidate Eval → Hidden → Artifact Acceptance
```

不是只显示在 UI 上。

## Candidate 与输出

对于复合业务 ZIP：
- ZIP 是 package container；
- AI Candidate Builder 接收 SemanticObject + ArtifactGraph；
- 只修改已读取/已知条目，不虚构缺失文件；
- Output Builder 在原 ZIP 上覆盖已验收变化，未修改条目原样保留。

对于 PPTX/DOCX/XLSX 等仍使用 V2.4 已验证的原生回写路径。
