# Evolve Studio V2.8 · Fast Experiment Runtime

## 1. 为什么 Candidate Experiment 会“像卡死”

V2.7 已经有并发、缓存和超时，但 Candidate Experiment 仍然存在结构性的调用乘法。

典型配置：

```text
6 Candidates × 8 Eval Cases
```

旧重型路径近似为：

```text
6 × Candidate Full Artifact Build
+ 48 × Candidate/Test Execution
+ 6 × Independent Candidate Judge
= 60 次重型 AI / Target 调用
```

这还没有计算 Schema 修正、Provider fallback、失败重试、Hidden Validation 等后续调用。

真正造成等待时间长的不是单一 timeout，而是：

1. 每个 Candidate 都先付完整 Artifact 构造成本；
2. Candidate × TestCase 形成乘法；
3. 同一 Candidate/Source 上下文被每道题重复发送；
4. 每个 Candidate 再单独调用一次独立 Judge；
5. Code ZIP 的 deep Repository Index 曾可能作为 structuredContent 重复进入 Build/Judge payload；
6. Provider fallback 串行发生时，会把多个 timeout 累加；
7. UI 以前只显示“运行 Candidate 实验”，用户不知道究竟卡在构造、执行还是 Judge。

## 2. V2.8 核心方案：Successive Halving

默认实验策略改成 `adaptive`：

```text
Candidate Population
        ↓
3 个高价值 Screening Cases
        ↓
批量 Artifact Runtime
        ↓
1 次 Population Judge
        ↓
6 → 3 Finalists
        ↓
只构造 3 个 Finalist Artifact
        ↓
完整 Eval Suite
        ↓
Independent Judge
        ↓
Winner
```

预筛不是最终评测。被筛掉的 Candidate 只保存 provisional screening score；Winner 只能来自完成 Full Artifact + Full Eval 的 Finalist。

用户可以在“进化方案”阶段切回：

```text
完整模式
```

用于高风险、候选数很少或必须对全部候选完整评测的项目。

## 3. Batch Artifact Runtime

新增 `execute-artifact-batch`。

旧：

```text
同一 Candidate
→ Test 1：重复发送 Source + Candidate
→ Test 2：重复发送 Source + Candidate
→ Test 3：重复发送 Source + Candidate
→ Test 4：重复发送 Source + Candidate
```

新：

```text
同一 Candidate + Source
→ [Test 1,2,3,4]
→ 一次模型调用
→ 返回 4 个相互独立的 Test Result
```

默认 `batchSize=4`。

Batch 只减少重复上下文和网络/模型启动开销，不允许一道题的 Evidence 替另一道题通过。

## 4. Code ZIP Overlay Fast Path

代码/普通 ZIP Candidate 如果 Patch 明确指向原 Manifest 中的文件：

```text
src/runtime.ts
src/features/evolve/foo.tsx
...
```

不再要求 AI 重写完整工程。

V2.8 本地直接构造：

```json
{
  "kind": "codebase",
  "overlay": true,
  "files": [
    { "path": "src/runtime.ts", "content": "...完整新文件内容..." }
  ]
}
```

运行/交付时：

```text
原 ZIP
+ changed-file overlay
= Candidate Artifact
```

未修改条目保持原样。

因此代码 ZIP 能命中 fast-path 时，Finalist 的 `build-candidate` AI 调用可以降为 0。

## 5. 上下文压缩

### Candidate Build

不再把完整 Repository Deep Index 传给每个 Candidate。

发送：
- repository digest
- critical modules
- relevant evidence
- compact semantic object
- 当前 Candidate 相关 Rubric

### Independent Evaluator

按当前 TestCase 的 `criterionIds` 只传相关 Acceptance Criteria。

单题 Review Budget：
- Candidate：約 5.2k chars
- Baseline：約 6k
- Holdout：約 7.5k

而不是每题固定把超长输出和整个 ArtifactGraph 再次塞入 Judge。

## 6. Baseline / Hidden Validation 同步批处理

V2.8 不只优化 Experiment。

### Baseline 8 Cases

旧逻辑调用模型：

```text
8 execute + 1 judge = 9
```

默认 Batch=4：

```text
2 batch execute + 1 judge = 3
```

逻辑调用减少约 66.7%。

### Hidden Validation 8 Cases

旧重型逻辑：

```text
8 baseline execute
+ 8 candidate execute
+ 2 judges
+ 1 release review
= 19
```

V2.8 Batch=4：

```text
2 baseline batches
+ 2 candidate batches
+ 2 judges
+ 1 release review
= 7
```

逻辑调用减少约 63.2%。

Fast Hidden Gate 同样使用 Batch。

## 7. Retry / Timeout 策略

V2.8 保留“长操作 timeout 后不立刻原样重跑”的原则。

只自动重试明显瞬时错误：
- 429
- 502 / 503 / 504
- network reset / fetch failed

不自动立即重试：
- timeout
- abort
- 大输出 Schema 失败的重型 Build

重型操作配置：
- `build-candidate`：75s、单 route、无完整 Schema retry
- `execute-artifact`：45s
- `execute-artifact-batch`：45s、单 route
- `evaluate-population`：40s、单 route

这样避免一次 60 秒 timeout 后再无意义付第二个 60 秒。


### V2.8 Watchdog：批量超时后不再自动扇出整批重跑

旧路径中，如果一次 Batch 已经等满 60 秒，随后再把 4 道题逐题 fallback，可能把一个 Batch 的实际等待翻倍甚至翻数倍。V2.8 最终版改成：

```text
Batch timeout / abort
→ 直接把本批题标记为执行失败
→ 继续后续 Candidate / Judge
→ 用户可用“只补考失败题”恢复
```

只有快速返回的非 timeout 错误才允许 per-case fallback；如果是 context/payload 过大，则先拆成更小 Batch 再试。

### 无可执行 Screening Case 时不做假预筛

如果当前 Eval Suite 全是 `external-runner / visual-review / manual`，Artifact Runtime 没有真实执行证据，系统会跳过 Successive Halving 预筛，而不是用 UNVERIFIED 结果随机淘汰 Candidate。

## 8. 运行状态不再只有一个 Loading

Candidate Experiment 现在分阶段显示：

```text
快速预筛 · Successive Halving
快速预筛 · Candidate X
快速预筛 · 独立 Judge
预筛完成 · 6 → 3 Finalists
构造 Finalist Artifact
完整实验 · Candidate X
独立 Judge · Finalists
实验完成 · Winner 已选出
```

运行条继续显示：
- Done / Total
- Percent
- Elapsed
- ETA
- Provider
- Model

因此即使某模型本身较慢，也可以判断当前到底在哪一层，而不是误认为页面卡死。

## 9. 默认实验策略

```json
{
  "mode": "adaptive",
  "finalistCount": 3,
  "screeningCaseCount": 3,
  "batchSize": 4,
  "buildConcurrency": 3,
  "batchArtifactRuntime": true
}
```

### 建议

普通 Agent / Prompt / Code / Workflow：使用默认自适应模式。

高风险、候选 ≤3、所有 Candidate 都必须保存完整审计证据：切换 `full`。

## 10. 调用数模型

见：`docs/release/v2.8-call-count-model.json`。

典型 6×8：

- V2.7 heavy path：60 calls
- V2.8 adaptive + code overlay：16 calls
- V2.8 adaptive + 3 finalist AI builds：19 calls

逻辑调用减少：68%–73%。

这不是实际墙钟时间 benchmark。真实时间仍取决于 Provider、模型、限流、缓存命中、外部 Runner 和 TestCase executionMode。
