# V2.2 AI Latency Analysis & Fast Path

## 1. Why V2.1 often felt "stuck loading"

The slowness was not one model call. A single user action could fan out into many long-running calls and large payloads.

### A. Candidate build was expensive

V2.1 could rebuild a complete Candidate Artifact with AI for each candidate even when the mutation could be applied deterministically. With 4-6 candidates this multiplies long-output generation cost.

V2.2 adds a deterministic local builder first:

- exact JSON / workflow path mutation;
- exact text/block replacement;
- full replacement for short complete prompt/template artifacts;
- Markdown heading replacement;
- structural runtime mutations can remain structured instead of forcing a full text rewrite.

AI full rebuild is now a fallback, not the default path.

### B. Candidate × TestCase execution multiplied calls

A population of N candidates over M test cases produces N×M target runs. V2.1 also had serial work in important paths.

V2.2 uses bounded concurrency:

- attachment extract/upload pool: 3;
- Eval Case pool: 5;
- flattened Candidate×Case pool: 6;
- Candidate evaluator calls: parallel;
- Artifact Acceptance batches: 2 workers.

Concurrency is bounded rather than unlimited so provider rate limits do not turn into retry storms.

### C. Repeated large Source context

The same Source Artifact could be injected repeatedly into Intake, Rubric, Plan, Candidate Build, Eval, Acceptance and Repair.

V2.2 adds context retrieval:

- heading/outline signals;
- requirement-keyword retrieval;
- relevant head/tail excerpts;
- integrity signals;
- compact source evidence for repeated operations.

Full Source remains the source of truth, but each operation receives the smallest evidence window that can answer its specific question.

### D. Artifact Acceptance used huge Original + Evolved prompts

A global acceptance prompt could contain very large Original and Evolved artifacts plus all rubric criteria.

V2.2 evaluates Rubric criteria in small batches. Each criterion gets the most relevant Original/Evolved excerpts plus outline/integrity signals. The runtime then computes the weighted score and hard-gate result locally.

This gives two benefits:

1. lower latency and token usage;
2. a hard criterion cannot be hidden by an average score.

### E. Long structured-output retry multiplied worst-case latency

When a large JSON-schema output failed validation, regenerating the entire long response could double or triple latency.

V2.2 operation profiles disable whole-response schema retries for the heaviest operations such as Candidate Build / Repair / Materialize, while keeping a limited retry path for short structured operations.

### F. Timeout retry could double a slow TestCase

Retrying an already timed-out 50-120 second target execution immediately creates the worst possible UX.

V2.2 does not immediately retry timeout/abort. Retries are reserved for transient rate-limit/network/502/503/504/reset cases.

### G. Provider fallback was fully serial

Every failed provider route could consume its full timeout before the next fallback.

V2.2 operation profiles cap the maximum routes for latency-sensitive operations. `execute-artifact` uses one route by default; compact reasoning operations may use a small fallback chain.

### H. OpenAI browser connection wasted time on CORS

The project already contained a Vite AI relay plugin, but V2.1 `vite.config.ts` did not mount it even though the documentation described relay behavior.

V2.2 actually mounts `aiRelayPlugin()` and official OpenAI BYOK uses the in-process relay first. This removes a known failed browser-direct attempt before the relay retry.

## 2. Result cache

V2.2 adds an exact-result cache keyed by operation + model route + normalized payload.

Typical TTLs:

- Candidate Build: 30 minutes;
- Artifact Materialize: 30 minutes;
- Artifact Acceptance: longer deterministic cache;
- Execute Artifact: 15 minutes for exact repeated payloads;
- short contract/eval operations: operation-specific TTLs.

The cache is intentionally exact. It does not fuzzy-reuse a result from a slightly different evolution command or artifact.

## 3. Performance telemetry

Settings now includes `AI Performance Diagnostics` and records:

- operation;
- provider / model;
- duration;
- input character size;
- cache hit;
- retry/fallback/error;
- average and P95 latency.

This is designed to answer "what is slow in my workspace?" rather than guessing from UI spinner time.

## 4. Contract-first also improves speed

V2.2 Intake returns the initial Project-specific Acceptance Rubric in the same first AI response as Source Understanding and Evolve Contract.

This removes a normal extra Rubric call during project creation. Recompile remains available only when the user edits requirements or explicitly requests it.

## 5. Remaining unavoidable cost

A real evolutionary system can still be expensive because high-quality search requires actual executions. If a project has:

- 6 Candidates;
- 8 visible tests;
- 4 hidden tests;
- independent AI evaluation;
- final Artifact Acceptance;

then dozens of model/target executions are legitimate work, not UI overhead.

The correct optimization is not to make these disappear; it is to:

1. eliminate duplicate/avoidable calls;
2. use cheap deterministic builders before AI rebuild;
3. use bounded parallelism;
4. route fast models to low-risk stages and stronger models to critical judgments;
5. cache exact repeated work;
6. expose per-stage progress and latency telemetry;
7. use staged evaluation so obviously bad candidates are eliminated before expensive Holdout/Acceptance.

## 6. Production next step

For production, move performance-critical orchestration to the backend:

```text
Browser
→ Evolution API
→ durable job / worker
→ provider gateway + server-side cache
→ Target Runtime
→ Eval service
→ immutable run store
→ progress events / SSE
```

This avoids browser lifecycle limits, enables provider-side prompt/cache controls, supports cancellation, and lets the UI stream granular progress instead of waiting on one long HTTP request.
