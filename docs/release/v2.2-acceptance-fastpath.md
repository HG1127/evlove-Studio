# V2.2 Acceptance-Driven Fast Evolution

## 1. Problem fixed

V2.1 introduced Acceptance Criterion types but the Rubric was still compiled after Target Ready and generic dimensions still dominated several runtime decisions. V2.2 makes the Rubric the actual contract and primary objective.

## 2. Contract lifecycle

### Intake
The first AI call returns both:
- Evolve Contract
- Project-specific Acceptance Rubric

This removes a normal extra AI request and lets the user see what “success” means before project creation.

### Target Ready
Target Ready validates:
- goal/metrics exist;
- Rubric has at least 3 criteria;
- weight total ≈ 100;
- at least one requirement derives from user/source;
- at least one Hard Gate exists;
- evidenceExpected is defined.

Test coverage is intentionally **not** required for Target Ready; the Eval Suite is generated after Contract confirmation. This avoids a circular dependency.

### Eval Suite
Every TestCase carries `criterionIds`.

Before Baseline:
- every criterion must be covered by at least one test;
- every Hard Gate must be represented in Hidden Holdout.

This validation is rechecked at runtime, not only in UI state.

## 3. Search objective

Experiment ranking:

```text
if Safety FAIL → reject
if any Hard Rubric Criterion FAIL → reject

objective = 84% Project Rubric Score
          + 16% generic diagnostics
          - cost penalty
          - latency penalty
```

Generic Accuracy/Evidence/Risk/Completeness cannot compensate for missing user requirements.

Best-Ever Campaign fitness also uses Rubric as primary objective and, after Artifact Acceptance, incorporates final Artifact quality.

## 4. Artifact acceptance

The same Rubric is reused against the exact Candidate Artifact Snapshot.

Acceptance judge is split into small criterion batches. Each criterion receives:
- original relevant excerpt
- evolved relevant excerpt
- outline
- integrity signals
- expected evidence

The runtime aggregates per-criterion results locally and applies Hard Gates locally, so an average score cannot hide a critical failure.

## 5. Repair

Repair targets only failed criteria. Ordering is:

```text
repair exact artifact
→ re-accept artifact
→ if still fail: repair again
→ when artifact passes: re-run Hidden once
→ deliver only when both pass
```

## 6. Latency architecture

### Removed/avoided repeated work
- Intake + first Rubric in one AI call.
- exact AI-result caching for deterministic/repeated payloads.
- deterministic local Candidate Build for executable JSON/exact/heading patches.
- long-context retrieval instead of repeated full Source injection.
- long structured outputs do not retry whole generation by default.
- timeout does not trigger immediate identical TestCase retry.

### Parallel work
- attachment extraction pool: 3
- Eval Case pool: 5
- flattened Candidate×Case pool: 6
- Candidate evaluator calls: parallel
- Artifact Acceptance workers: 2

### Provider routing
Official OpenAI BYOK uses the in-process relay first because its public API is not browser-CORS oriented. Other providers use direct fetch when possible and relay on CORS failure.

## 7. Remaining production work

For truly large code/system artifacts, browser runtime is still not a production-grade Artifact Builder. Production should use:

```text
Git/workspace snapshot
→ apply structured mutation
→ typecheck/lint/test/build
→ benchmark
→ immutable Candidate Artifact
→ evaluator
```

and persist Rubric/Eval/Artifacts/Runs in the backend.
