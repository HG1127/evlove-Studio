# V2.6 · Parser-first Evidence Architecture

## 1. 本轮真实问题

用户上传 Evolve Studio ZIP，命令是：

> 进化该系统，从系统成果物输入兼容、流程完整闭环、UIux更符合产品审美和操作习惯等角度去进化。

V2.5 实际 Baseline 却出现：
- `media/composite` 是否有独立 typeId；
- `semantic-evolution.ts` / `workflow-engine.ts` 内部实现；
- Tailwind token 是否在文本 chunk 中完整出现；
- Demo Artifact Runtime 的占位输出；
- 六步状态是否有 undefined 断点。

这说明系统发生了“证据源漂移”：测试/文档/源码内部实现细节被误当成用户最终目标。

## 2. 结论：主要是解析与证据建模问题，不是单纯 API 问题

模型 API 会影响理解能力，但根因主要发生在模型调用之前与之后：

1. ZIP 选择上下文时，测试 fixture / release docs 权重过高；
2. Parser 把结构证据与业务目标混在同一个扁平文本；
3. TestCase 没有声明“这条标准需要什么证据”；
4. Code ZIP 的 Demo Artifact Runtime 被当作真实用户行为 Runner；
5. 缺少 E2E/视觉能力时，系统把“无法验证”转成 FAIL；
6. Rubric 太多、太内部化，用户命令没有成为确定性锚点。

所以只换更强模型不会根治。

## 3. ZIP 解析 Pipeline

V2.6 对 ZIP 使用：

```text
ZIP Container
↓
完整 Manifest
↓
Entry Role Classification
  implementation
  configuration
  content
  documentation
  test-evidence
  reference-evidence
↓
Priority Index
↓
Nested Office/PDF Parse
↓
Code AST / Import Graph
↓
Artifact Graph
↓
Semantic Object
↓
User Intent Anchors
```

测试、fixture、release docs 仍保留为证据，但不再决定 Semantic Object。

## 4. Codebase 判断更保守

ZIP 只有满足以下之一才进入 software/codebase：
- 存在真实项目 manifest：package.json / pyproject.toml / go.mod / Cargo.toml 等；
- 存在 src/app/lib 等工程目录，并有足够代码文件；
- 代码文件数量达到高置信阈值。

仅仅出现 `components/` 目录不再等于代码工程。

## 5. User Intent Anchors

V2.6 从用户原命令确定性生成高优先级标准。

本次真实命令稳定产生：

```text
USER-INPUT-COMPAT      成果物输入兼容      external-runner
USER-WORKFLOW-CLOSURE  流程完整闭环        external-runner
USER-UIUX              UI/UX 与操作习惯     visual-review
```

这三项会压住模型自己生成的内部实现型 Criterion，避免目标漂移。

## 6. Internal Coupling Sanitization

除非用户明确要求修改某个内部文件，否则下列词不允许成为主要产品验收目标：
- `src/*.ts / *.tsx`
- typeId
- semantic-evolution
- workflow-engine
- Tailwind / CSS token / theme token
- test-results / playwright / vitest
- release report / fixture

内部结构仍可以作为 Supporting Evidence，而不是 Product Outcome。

## 7. Mature Parser Gateway

V2.6 增加可选 Parser Gateway：

### Docling
适合 PDF、DOCX、PPTX、XLSX 等结构化文档；可转换为统一文档结构，并导出 JSON/Markdown/Text。

### Unstructured
适合多文档自动分流，可按 fast / hi_res / OCR/VLM 等策略权衡速度与版面精度；能保留 Title、Table、Header、Footer、CodeSnippet 等元素类型。

### Apache Tika
适合作为广谱格式探测、元数据和文本抽取底座，尤其适合“先识别这是什么，再决定交给哪个专用 Parser”。

### Tree-sitter
推荐作为生产级多语言代码结构底座：生成 concrete syntax tree，支持增量解析，并能在语法错误情况下继续给出有用结构。

V2.6 前端本地版本当前使用已有 `@babel/parser` 对 JS/TS/TSX/JSX 建 AST，不新增 npm 依赖；Tree-sitter/ts-morph 更适合后端 Parser Worker 阶段引入。

## 8. Evidence-aware Validation

验证现在按：

```text
Criterion
↓
validationMethod
↓
TestCase.executionMode
↓
Run.verificationStatus
↓
Criterion.verificationStatus
```

### 主 UI 行为
- verified hard failure → 红色失败；
- unverified hard criterion → 黄色“待真实证据”；
- partial static evidence → 黄色“部分证据”；
- release 必须所有 hard gate 有真实证据才能进入。

因此不会再出现截图中“当前 Runtime 根本没有视觉/E2E 能力，却把 UIUX/完整闭环判成大量红色失败”的误导。
