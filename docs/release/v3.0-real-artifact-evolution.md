# V3.0 · Real Artifact Evolution Workflow

## 为什么重构

之前系统底层已经有 Parser、Semantic Object、Candidate、Hidden Validation、Artifact Acceptance，但用户主流程仍然暴露大量工程节点，且不同 AI Operation 经常收到类似的通用 Source 摘要，容易造成“流程看起来完整，节点实际上没有围绕当前问题深入读取成果”的体验。

V3.0 把主流程收敛为 5 步，同时要求每一步都有明确的读取范围和用户可理解的产出。

## 5 个用户步骤

### 1. 看懂成果
回答：系统到底读到了什么？用户真正希望什么变好？

内部执行：
- Artifact parsing / Repository Intelligence
- Semantic Object
- Evolve Contract
- Acceptance Rubric
- Eval Suite
- Baseline

### 2. 找出关键差距
回答：当前最值得改的问题是什么，真正原因在哪里？

内部执行：
- Failure Map
- Problem priority
- Trace comparison
- Root Cause + Evidence + Counter-evidence + Falsifier

### 3. 生成并比较新版
回答：针对根因，哪些真实新版更好？

内部执行：
- Candidate Population
- Artifact-specific Builder
- Deterministic/Overlay Fast Path
- Sandbox / Batch Runtime
- Independent Judge

### 4. 验证是否真的变好
回答：新版是否满足用户最初要求，而不是只会做已知题？

内部执行：
- Hidden Validation
- Project-specific Rubric
- Artifact Acceptance
- Repair Loop
- VERIFIED / PARTIAL / UNVERIFIED / FAIL evidence states

### 5. 交付最佳成果
回答：用户最终拿到什么，能否继续使用？

内部执行：
- Freeze accepted snapshot
- Same-format materialization
- Output package / versions
- Optional Shadow / Canary
- Lesson / Skill / Next Queue

## Stage-specific Artifact Retrieval

V3.0 的 `sourceEvidence(project, focus)` 不再固定截取每个 Source 的开头文本。

每个 Operation 都带 `readFocus`，例如：
- Problem：围绕失败、用户目标、受影响流程检索
- Diagnosis：围绕选中问题检索相关模块/段落/依赖
- Plan：围绕根因、可修改区域、保护边界检索
- Campaign：每轮基于 Search Champion + 当前问题重新取证
- Copilot：围绕用户当前问题读取相关成果证据

长文本使用 `retrieveTextContext()` 做 head/tail + relevant chunk 检索；代码 ZIP 继续依赖 Repository Intelligence / Requirement Evidence。

## 为什么这比继续增加节点更重要

进化的本质不是“执行更多 AI 调用”，而是：

```text
用户目标
→ 读取真实成果
→ 找到有证据的问题
→ 修改真实成果结构
→ 对完整新版验收
→ 交付同一新版
```

如果任一环节只处理抽象摘要或修改建议，进化就会退化为“AI 咨询”，而不是 Artifact Evolution。
