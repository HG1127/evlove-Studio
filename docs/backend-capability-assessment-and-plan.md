| Area | Implemented capability | Current boundary |
| --- | --- | --- |

## Confirmed gaps

1. **Validation evidence atomicity:** validation records persist in the immutable Event Store and support idempotent retries. Writing the follow-on signed Evidence Ledger record is a separate operation. A retry with the same idempotency key checks the authoritative Event identity, completes a missing Event Evidence mirror, then completes the validation-specific Evidence record. Concurrent identical requests recover the canonical stored result; changed requests still conflict. The governed Validation Evidence reconciliation route can complete both signed records from a persisted Validation ID, including one created without an idempotency key. A lost response to an unkeyed request can be investigated through the bounded Mission-scoped Validation discovery API; the caller must know the Mission and follow Event cursors until the scan is empty. An ambiguous Event append now checks the exact authoritative Event before failing and returns the attempted Validation ID when persistence remains uncertain. A later database commit may still require operational investigation; prefer a caller idempotency key for safe retries.
2. **Artifact lifecycle atomicity:** blob bytes and metadata persist through the Artifact Store; registration and evidence/Event writes remain separate operations. The Artifact reconciliation API replays missing audit writes from stored bytes after checking identity and hash. Binary compatibility uploads have a 20 MiB request cap; metadata failures retain bytes for recovery. Tombstone-driven cleanup and its migration are applied and PostgreSQL-tested; an active orphan-blob removal on production remains unverified.
3. **Lifecycle consistency:** Job creation, transitions, Workflow Job Store writes, cancellation, and checkpoint writes now use transactional RPCs with Events. Signed Evidence is still a separate write and relies on deterministic retry/reconciliation.

Checkpoint validation and acceptance now recover a committed audit Event when a repeated validation ID collides with its original timestamp. Recovery reads the exact authoritative Event ID, checks all fields except the independently recorded occurrence time, and mirrors the persisted Event before retrying the deterministic checkpoint Evidence append. A different decision, Artifact binding, or scope remains a conflict; a transient mirror failure returns 503. This also recovers Events created before the retry fix without changing their original acceptance time. Local fault-injection tests cover a failed Evidence append, duplicate Event replay, mismatched decision, and mirror failure. ### P1 — Recoverable Artifact and validation lifecycle (implemented in code)

- Added Zod request/result contracts for Artifact registration and Validation.
- Artifact registration now stores Mission/Job/type metadata and server-computed SHA-256 with the private blob. An existing Artifact ID cannot be rebound across Missions or reused for different bytes.
- Artifact registration reconciliation rechecks the persisted Artifact ID and any saved Job's Mission before replaying Event and Evidence writes. A missing Job or changed binding returns a conflict.
- Validation records persist in immutable Event payloads; GET reads the Event Store.
- Implemented SHA-256, minimum/maximum byte length, and UTF-8 text-presence checks with explicit per-check evidence. Unsupported/no checks remain unverified.
- A passed Validation now also requires durable Artifact metadata to identify the requested Artifact ID, match the observed byte length, and carry the exact requested Job binding when one is supplied. Missing or different bindings produce a failed Validation and cannot unlock Checkpoint acceptance.
- Validation reads any Artifact-bound Job from the durable Job Store and requires the exact Job ID and Mission. When a request omits `jobId`, the saved Artifact Job still flows into the Validation Event and its signed Evidence rather than disappearing from the audit chain.
- Checkpoint acceptance now requires a persisted passed result carrying the exact Artifact hash.
- Checkpoint acceptance re-reads durable Artifact metadata and bytes, verifies Mission, size, and SHA-256 against the passed Validation, and rejects drift before writing an acceptance Event or Evidence.
- Checkpoint acceptance also compares durable Artifact Job binding with the authoritative saved Validation when that Validation names a Job. A missing or different Job binding blocks acceptance before signed Evidence or Checkpoint Event writes, including retries of older passed Validation records.
- Checkpoint acceptance now replays every persisted deterministic Validation check against the exact Artifact bytes and hash. Empty, failed, duplicated, unsupported, malformed, or contradicted check receipts cannot unlock acceptance, even if an older Validation Event claims `passed`.
- Checkpoint validation and acceptance complete the source Validation Event mirror and deterministic signed Validation Evidence before writing a Checkpoint decision. Missing or mismatched source Validation identity blocks the decision.
- Validation POST accepts an idempotency key; a retry with the same key and request returns the persisted result, while reusing the key for another request returns a conflict.
- Validation POST returns the persisted Validation ID in a 503 error when a follow-on Evidence write fails. `POST /api/evolution/validation/:id/evidence-reconcile` reads the authoritative Event, completes its signed Event mirror and deterministic validation-specific Evidence, and can be retried by ID without rerunning Artifact checks.
- `GET /api/evolution/validation` scans authoritative Events by Mission and optional Artifact in bounded pages, returning validated persisted Validation results and the Event cursor even when a page has no matches. This lets an operator recover the ID from a lost unkeyed response without trusting a browser cache or treating an incomplete first page as the full history.
- When Event append loses its response, Validation tries an exact authoritative Event readback and completes its signed Event mirror before returning the canonical result. If the write cannot be confirmed, the HTTP 503 includes the attempted Validation ID. A caller can look up that ID and reconcile Evidence if it appears, without assuming a failed append or creating a second unkeyed Validation.
