# Run source-grounded browser predicates within the native HTML profile

Status: accepted. This extends the existing execution route without changing acceptance thresholds.

The confirmation SOP's protection case retained its frozen nine-step search plan. The native executor excluded every case with explicit browser steps, so that case received only the ordinary search smoke result. Other cases' native receipts could not establish that this case's predicates had run.

The Core recognizes only the exact source-derived search plan, including its previously frozen nine-step variant and the current twelve-step variant. Custom, altered, reordered and incomplete plans retain the ordinary route. Both the server composition and adapter recheck the plan against the SHA-verified physical Original before transmitting it. A versioned, bounded Zod contract carries only source-derived actions, selectors and values; it excludes TestCase questions, expected answers and prose.

One ephemeral, network-denied native execution can execute both distinct plans alongside the complete existing profile. Every plan starts with a fresh page, every declared step produces its own measured check on both Original and Candidate, and a final reload restores the full profile's initial state. The existing Runner's visible, fill, count and text-includes semantics remain unchanged. Action failures and assertion failures are recorded; restoration predicates are still attempted. No proof from another test case is retagged to supply missing steps.

The observation's optional `browserAssertions` field has its own `source-grounded-browser-assertions-v1` version. Old observations remain readable for cases without declared steps; they cannot prove a stepped case. Completeness checks require the exact ordered plan and all per-step results on both physical subjects. Normalization, criterion settlement and checkpoint reuse enforce this binding. A negative Candidate assertion cannot be overridden by a positive Judge score. A positive physical profile still requires independent semantic assessment and does not establish final acceptance or user benefit.

The kernel hash, evidence policy version and measured review version change, invalidating incompatible execution and score reuse. Historical failures, frozen suites, physical artifact identities and final questions remain unchanged. The review receives check IDs/counts and plan step counts, rather than raw assertion values.

Validation uses contract, Core, Harness, adapter and composition regression tests, including the trusted step function with a synthetic page port. It does not execute user HTML on the host. Any new paid end-to-end confirmation requires its own authorized budget; local checks do not retroactively change a past trial's verdict.
