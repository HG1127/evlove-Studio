## Decision

Core retains all existing pure layout, Original-code, paragraph-budget and numbering policies. Backend composes their checks before any file write. If layout compilation succeeds, independent post-compilation checks are collected together. If it fails with its known layout error, the remaining checks inspect the raw proposal and are explicitly labelled `before-layout`; these are preliminary diagnostics, not claims about final compiled bytes. Unknown compiler/read/provider errors propagate unchanged.

Two or more distinct known static failures produce `html-construction-feedback-v1`, containing each existing bounded correction detail and exactly one copy of the invalid proposal. A single failure keeps its original error/feedback behavior. No per-error retry is introduced: build and repair still share their existing single pre-write construction correction. The corrected result restarts full layout compilation and every static check, and must later pass all unchanged native, semantic, Hidden, independent-final and acceptance gates. A partial correction stops without writing a frozen file. Layout changes can reveal further problems; this mechanism reports everything currently observable and does not promise one correction will succeed.

Only internal measured error instances qualify. The model's proposed artifacts retain the existing Zod-validated boundary. No source program, key, independent-final question or evaluation result is added to the diagnostic context. No historical verdict, byte identity, repair budget, deadline or scoring policy is rewritten. The architecture remains contracts ← core ← harness ← apps; this composition adds no dependency exception or infrastructure.
