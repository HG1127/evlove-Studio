# Physical HTML observations and bounded construction correction

Status: implemented for validation, 2026-10-23.

The real SOP pilot exposed two different evidence gaps. A Judge could not verify script/style preservation from document text alone. A later AI construction proposed an exact replacement anchor absent from the physical Original, so strict materialization correctly stopped before writing a file. Neither event proves a passing deliverable.

## Physical observations

Core compares HTML5 parsed script/style blocks, stylesheet references, the element tree and attributes, and actual slide-card order. These are factual observations, not quality or runtime verdicts. Syntax normalization, external resource bytes and inactive template descendants remain explicit limitations.

The backend static executor reads the Mission-bound Original Source Blob and its authoritative metadata, checks ID, Mission, kind, size and actual SHA-256, and independently checks the frozen Candidate bytes against their SHA-256. Only hashes, counts and comparison booleans enter the existing static execution record. No HTML, script, style or control fragment is added to model inputs. Missing or mismatched physical identity leaves this comparison unavailable; it does not fabricate product failure or preservation success. Independent semantic quality, actual browser execution, the original rubric and all final gates remain required.

The execution policy version participates in Experiment recovery and Hidden context fingerprints. Old observations and assessments cannot silently stand in for the new physical evidence route. The complete primary Original Baseline scoring route remains unchanged; search history and the original thresholds are retained.

## Construction correction

Core emits a typed `ExactEditAnchorError` when strict matching cannot find one unique anchor. The builder may make one additional construction request using exactly the same source context, the AI's invalid proposal, and the failed edit index. It does not add source fragments, tests or final-paper feedback. Strict validation runs again, and all Targets are prepared before the first frozen write.

A second invalid proposal stops. Protection, schema-mode, storage, hashing and other errors cannot trigger this correction. A frozen or partially persisted file is never regenerated through this path. This is construction repair before any Candidate exists as a physical file, not a way to repair a failed independent final test. The pre-reserved final paper and historical failed attempt stay unchanged.

Domain policy remains in Core, recovery orchestration in Harness, and physical storage/model calls in backend composition. No new infrastructure or dependency-direction exception is introduced.
