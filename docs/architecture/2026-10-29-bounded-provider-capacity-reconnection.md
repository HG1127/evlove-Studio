# Reconnect an explicitly capacity-rejected provider request

Status: implemented. Related regression checks passed across 26 files in two completed batches: 489 tests in 25 files, followed by all 16 tests in the one file whose worker first exited with an out-of-memory error. The resource failure is retained. Architecture, changed-file lint, all 11 Runner tests and the complete TypeScript/production build passed.

The user added automatic reconnection for network fluctuations and “Selected model is at capacity. Please try a different model.” The direct-provider adapter already reconnects once for a classified connection failure, within the same signal. It previously returned every HTTP response without capacity recovery.

The same single reconnection allowance now also covers a fully received explicit capacity rejection on HTTP 429, 503 or 529. JSON errors are validated with Zod; a short plain-text rejection is also recognized. A response carrying model output is retained without reconnection. The adapter preserves the same URL, request object, body, model, credentials and original abort signal, waits 250 milliseconds and checks cancellation. A network failure and a capacity rejection share one allowance; no third physical attempt is added. Ordinary HTTP failures, authentication/payment limits and model-result/schema failures retain their prior handling. Interrupted bodies and provider timeouts still have unknown remote completion and are not regenerated by this change.

The server usage observer records a capacity rejection as its own response before another physical start. Failed/unknown usage is retained, and two attempts are never collapsed into one billed or successful call. Raw provider errors, source text, URLs and credentials are excluded from the canonical usage records. A completed result is never repeated to repair a failed telemetry write. Existing format correction and paired-scoring semantics remain separate; no successful score is resampled and no model or pricing route is silently changed. The SDK gateway retains its existing behavior.

C40's actual protected-case execution received HTTP 402, “Hobby plan usage limit exceeded,” with reset time `2026-11-01T00:00:00.000Z`. That is an observed free-tier limit, not a reconnectable capacity rejection. No purchase, upgrade, new isolated environment or paid fallback is introduced. Full native confirmation remains unavailable until free capacity is restored or a separately authorized suitable free environment exists.

Tests cover capacity recovery, original body/signal identity, bounded repeated rejection, shared reset/capacity allowance, abort during backoff, retained completed output, response readability, nonretryable 402 and independent usage records. C40 itself had no provider transport failure or capacity rejection; these tests do not claim a real external outage occurred or that the evolution goal is complete.
