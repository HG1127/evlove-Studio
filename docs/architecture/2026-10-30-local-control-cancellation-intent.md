# Local control intent outside the observed backend

D1's localhost guard shares the observed backend's failure domain. The existing native process observer now optionally binds Mission, Job, Run, source commit, entrypoint hash and absolute deadline before launching its owned process. The local adapter validates this operational boundary with Zod and exclusively creates each binding and cancellation intent. A timeout terminates the owned process at the original deadline, then records intent; nonzero and supervision failures also record intent. The prewritten binding keeps cancellation required after deadline even if supervision is lost before that write. The first intent is never overwritten.

The I/O adapter remains in tools/local-runner with the platform-specific observer. It performs local operational validation, not Domain promotion logic, and adds no control platform. Core/Harness gain no dependency on PowerShell or filesystem.

An intent is not a cancellation receipt. Inspection after deadline returns cancellation-unconfirmed even if the controller died before writing an intent. It never reports running from an old checkpoint, releases a scoring claim, repeats a generation, restarts a Job or claims an unreachable backend cancelled it. The governed owner must reconcile the exact identity against authoritative state under existing permissions.

Tests use trusted local substitutes for nonzero exit and absolute timeout, plus immutable/rebound intent and lost-controller cases. This is offline failure-boundary evidence, not application-load lifetime evidence, a C44 exit-cause diagnosis, or authorization for a new Mission. Application and cross-order calibration gates remain required.

## Authoritative reconciliation

The local adapter now exposes `reconcileControlSession` with injected, governed status-read and optional cancel ports. It provides no network transport or permission grant. The status port must query the supplied Job and Run against the authoritative controller. Zod validates the response subset; Job ID and Mission ID must match the immutable local binding. The Run must be explicitly bound by Job metadata or by the existing legacy backend rule: a campaign Job with a `workflow-control:` idempotency key and a matching `outputRef`. If both bindings exist, both must match. Missing or conflicting bindings fail closed; a Run supplied only in the query does not bind a Job. Mission-schedule-only fallback is not supported without independently read canonical Mission evidence. Events, prompts and other response payloads are not persisted.

Reconciliation runs only when cancellation is required. Deadline-derived intent is persisted before any external call. An immutable local attempt is reserved before cancellation I/O, so a rejected request, process crash or unknown outcome cannot trigger an automatic second cancel. Later recovery can read authoritative status without sending another cancel. An unreachable controller leaves cancellation unconfirmed. Both Job and Run must be terminal before an exclusive terminal receipt is saved; a completed Workflow with a waiting Job remains unconfirmed. Natural completion or failure confirms a terminal state, not cancellation. Cancellation is confirmed only when both statuses are cancelled. Existing intent is retained separately. A saved receipt is an observation at its recorded time, not a claim that mutable remote state was continuously monitored.

Tests exercise identity mismatch, controller loss, unknown cancellation outcome, recovery without resend, terminal mismatch, natural completion and receipt rebinding. They do not claim live API reconciliation or application-load admission. Wiring this adapter into a concrete diagnostic owner remains necessary before a new trial.

## Execution cutoff and bounded process cleanup

The observer accepts an explicit `CleanupGraceSeconds` from 0 (the unchanged default) to 60. The original execution deadline still must be within 30 minutes and still binds cancellation intent. It is never extended in the binding or event records. At that cutoff the observer records intent and a separate deadline event; only physical process cleanup may continue until the separately recorded cleanup deadline. A natural exit in that interval retains its real exit code and `executionDeadlineReached: true`; a process still alive at the cleanup deadline is forcibly terminated and reports `deadlineStop: true`. Neither result alone proves application admission.

The trusted child receives separate original-execution and process-cleanup deadline environment values. This supervisor is not an outbound-request security boundary: the governed child/controller must independently prohibit new model or trial work after the original cutoff. Grace grants no retry, registration, request or spending authority. A real diagnostic or trial composition must verify that enforcement before using grace. Tests establish local intent timing, unchanged identity, natural cleanup, physical hard stop and rejection above 60 seconds; they do not prove a production model gate.

Read-only diagnostic owners may explicitly request up to 60 seconds of `DiagnosticStartupAllowanceSeconds` in addition to a 30-minute observation window. This is separate from cleanup grace and is rejected whenever an execution control binding is supplied. The default remains 30 minutes, and bound execution initialization still enforces its original 30-minute maximum. The allowance lets a diagnostic start its full measured workload after backend readiness; startup and cleanup must be reported separately and cannot establish workload duration. It grants no Mission/model authority. The diagnostic composition must independently deny provider calls and remote writes, pin its scenario and enforce its own fixed workload window. Tests cover explicit longer observation, unchanged default rejection, bound-execution rejection and the 60-second cap.
