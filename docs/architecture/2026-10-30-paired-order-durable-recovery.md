# Durable paired-order observations without fresh scoring authority

The integrated contract is `paired-order-observation-v2`. Every saved order additionally contains the request-local `server-ai-response-provenance-v1` observations from its real gateway invocation, including any fully received format-correction replies. Each carries a physical usage call ID, trusted Mission/Job, operation/model/protocol identity, exact issued order fingerprint, request-body text hash and complete decoded HTTP response-body text hash. The canonical parsed-result hash remains separate. Production validates physical route tuples against the pinned connection's effective evaluator configuration. SDK routes without complete HTTP-body provenance fail before claiming or generating. Both orders must have distinct physical call identities. No response text, prompt, credential or raw script is copied into the provenance metadata.

The original durable physical claim key is unchanged. Version-1 order Events without this provenance are not silently upgraded, and an already occupied claim never grants another request. Both version-2 orders must pass schema, source/hash/paper/route/Job and raw-order identity checks for zero-call recovery. One confirmed order still blocks the unknown remainder. Default request-local provenance is enabled only inside a paired invocation that uses a durable journal; injected non-journaling diagnostic ports retain their explicit behavior. Fault tests use synthetic data, including actual gateway code with substituted HTTP and Event I/O. They do not constitute live model calibration or a real SOP acceptance.

D2 is distinct from C44's runtime loss: C44 never reached judgment. The paired comparison still reserves the original durable physical claim before generation. Each validated order is now appended and canonically read back as a versioned Event before proceeding. The contract binds complete parsed response/hash, Mission/Candidate, file/paper/rubric, request fingerprint and scoring route. Contracts declare the journal port, Harness validates recovery and the backend supplies Event I/O.

If both orders are durably confirmed, recovery assembles the original conservative receipt with zero new model calls and without replacing the claim. One saved order remains readable but cannot authorize the remaining unknown outcome; it fails closed. Legacy occupied claims without saved orders still block. No claim is released, renamed, made fresh or rejudged; low/negative scores, Safety FAIL and conflicts are retained. A validated response lost before its durable write remains an explicit unknown, not permission to sample again.

Fault tests cover partial first-order persistence, second-response persistence failure, and replay after both orders saved but before Mission persistence. Canonical Event readback, complete lookup and trusted same Job scope are mandatory. Different model/file/paper, altered/invalid response, wrong scope or duplicate order block recovery. Persistence is code only until deployed; no production Event, migration, Job or historical Mission is changed by these tests.
